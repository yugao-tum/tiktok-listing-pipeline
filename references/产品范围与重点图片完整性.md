# 产品范围和重点图片完整性（v1.6）

完整性分三件事：要求的颜色／规格是否全部进入队列；每个变体是否交付完整购买信息；采用原图和采用译图是否全部进入交付文件夹。单变体 QA 通过不能代表整个型号完成。

## 建档：型号不等于一个变体

先沿用用户已确认的范围。用户只指定型号或产品链接且要求完整 listing 时，枚举该型号的颜色、尺寸和配置；用户明确只要一个颜色／规格时保留该边界。不能用网页默认选项代替范围，也不能把混型号链接中的全部型号自动纳入。身份无法判定时先研究；只有会改变范围且不能从现有证据判定的情况才问用户。

建立一份共享的 `产品批次/产品范围/<型号>.json`，逐项对齐官方产品快照。`excluded_variants` 仅表示本子任务不得混用的变体，不代表整个型号不需要这些变体。所有需要的变体都分配子任务编号，分轮执行的上限不是总规格上限。缺货保留为 `deferred` 和原因，计入未完成；只有明确的用户范围或其他型号证据才能排除。

```json
{
  "family_id": "MODEL-A",
  "requested_scope": "all_model_variants",
  "scope_evidence": "用户要求该型号全部颜色；记录其消息或已确认范围来源",
  "snapshot": {"file": "产品批次/证据/model-a.json", "sha256": "实际文件完整哈希"},
  "variants": [
    {"variant_id": "123", "sku": "MODEL-A-BLACK", "options": ["Black"], "disposition": "required", "product_id": "MODEL-A_BLACK"},
    {"variant_id": "124", "sku": "MODEL-A-WHITE", "options": ["White"], "disposition": "required", "product_id": "MODEL-A_WHITE"}
  ]
}
```

`requested_scope` 可为 `all_model_variants` 或 `exact_variants`。`snapshot` 为官方 Shopify `product.js` 或 `product.json` 快照；非 Shopify 先整理为有 `variants:[{id,sku,options}]` 的证据文件，保留原始来源。所有快照变体必须分类一次，SKU、options 必须一致；`excluded` 另需 `reason_code: user_excluded|other_model`、`reason` 和具体 `evidence`。脚本核对引用和完整性，不能代替对型号归属及用户意思的判断。

每个 `产品任务.json` 增加 `scope: {file:"产品批次/产品范围/<型号>.json", sha256:"实际完整哈希"}`。路径相对工作区；scope 变更后只更新受影响子任务引用并重跑必要 QA。不能为通过检查伪造排除依据，也不能把范围表缩为已做完的几个。初始化已知变体时即校验范围；身份未定的研究任务仍可排队。

## 选图：先保留信息，再决定用哪张图

在选图前，从用户要求、官方事实和主图库已识别内容建立 `图片审计/购买信息需求.json`。初筛发现新重要信息就补入基线，再定稿最终序列。仅列影响购买判断的内容，不把每句营销话术变成一项任务。通常核对目标外观／颜色、选型尺寸、核心功能、控制器或操作方式、结构细节、必要的配件与使用场景；是否必需取决于该产品。

```json
{"requirements":[
  {"id":"dimensions", "title":"尺寸与适用空间", "required":true, "source_evidence":"官方尺寸字段或图片编号及哈希"},
  {"id":"decorative_scene", "title":"第二种装饰场景", "required":false, "source_evidence":"主图编号及哈希", "omission_reason":"与已采用场景没有新的选购信息"}
]}
```

初筛条目增加 `requirement_ids:[]`，将图片的信息关联到需求 ID；纯装饰、其他型号无关信息可为空。**错误颜色的图可能承载目标型号的重要功能；排除图之前先保留经官方证据确认适用的需求。** 对每项缺口按顺序：复用合格正确图 → 查看目标款其他主图 → 补明确的官方详情图／共享组件图 → 在授权范围内修复 → 记录阻塞和下一步。不能直接用其他颜色整机图冒充目标款，也不能靠删需求“修复”缺图。

产品 GPT 对话审阅基线，审计文件记录 `requirements_sha256`。必需项不能因难做变成可选；真正的可选项写具体省略原因，用户明确交付项只有用户范围变更才能取消。基线调整保留原因，新的基线哈希使旧审查和 QA 失效。

## 终审：绑定实际交付图

保留现有 `required_roles` 和 `role_coverage` 来源追溯；它们不再单独证明信息完整。`final_sequence_review` 另需：

```json
{
  "information_completeness":"PASS",
  "requirement_coverage":{
    "dimensions":[{"rank":2, "output_sha256":"实际最终图完整哈希", "visible_region":"右下角尺寸箭头及标签", "shows":"目标规格的宽深高，文字清楚且无裁切", "status":"PASS"}]
  }
}
```

由产品 GPT 对话查看实际文件，指出哪一张、哪个区域、展示什么、是否清晰。这里的哈希是最终序列 `asset` 的文件哈希：原图直接采用则绑原图，译图采用则绑译图。不能用源图哈希替代译图，也不能用一个控制器裁图笼统证明整副桌架细节。一图可以覆盖多项，但每项都有具体可见依据。

3～4 张不自动判失败，也不自动算完成；重点检查是否过度去重、把不需翻译的原图漏出序列、把唯一重要信息随错误变体图删除。只要有明显新增购买信息的合格主图就保留；相同图片字节不重复交付。无明确平台限制时，不以压到最少张数为目标。

## 交付和汇报

统一序列含**全部采用原图＋全部采用译图**。均按 `NN_<中文内容名>.<ext>` 命名，汇总到固定 `上架交付/<子任务编号>/图片/`，不需要翻译不是不需要交付。译图替换其对应外语原图，不重复放两份。交付清单核对原图数、译图数、总数和每个文件哈希；相同文件复用，不新建日期副本。

单变体 QA 通过时明确为“该变体通过”。型号全部完成需执行只读汇总：

```powershell
python scripts/核对产品范围.py --workspace "<工作区>" --scope-file "产品批次/产品范围/<型号>.json"
```

它对齐全部应做规格、最新 QA 和真实交付文件；`not_queued`、`deferred`、`incomplete` 都不计完成。`--output-root` 支持已明确的自定义交付根目录。汇报“型号 A：应做 N，交付 M，缺口及原因”；不要用完成一个默认规格折算为完成一个整型号。

v1.6 不自动重跑旧商品，也不修改已有交付。旧版 PASS 不具备新完整性证据，续做时补范围和需求、复用仍有效的原图／译图判断，仅处理缺口，再跑新版 QA；不得把历史合格文件说成视觉不合格。

## 提速边界

型号范围和公共事实一次确认，子任务引用；共同来源只抓主图区，下载复用已有哈希。原图不需翻译就直接入序列。先做需求和全图库初筛，再集中精审／翻译；复用与变体、需求和文件一致的结论。范围或需求改变时优先复查变化影响，不能以提速为由沿用不适用的结论。常规绑定、命名、去重、汇总用脚本；GPT-6 处理身份、重要信息取舍和复杂修复判断。代理调用条件与模型等级沿用多智能体规则，不因颜色变多就自动启动更多代理。
